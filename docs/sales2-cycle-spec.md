# فروش ۲ — مشخصات چرخه‌ی سند (پیش‌فاکتور → فاکتور → حواله → مرجوعی)

وضعیت: تأییدشده برای پیاده‌سازی · ۱۴۰۵/۰۷/۰۱

این سند پنج قاعده‌ی تأییدشده را یکپارچه می‌کند. مبنا:

```text
ردیف پیش‌فاکتور → چند ردیف فاکتور → مانده ← حواله / مرجوعی کالا / کسر تحویل‌نشده / بستن
```

**اصل پایه: هیچ مانده‌ای ذخیره نمی‌شود.** همه‌ی مقادیر زیر از اسناد صادرشده حساب می‌شوند. وضعیت‌های «بخشی/کامل» هم از همین محاسبه درمی‌آیند. تنها چیزی که ذخیره می‌شود تصمیم انسانی است: بستن، ابطال و دلیل.

---

## ۱. مدل داده — تغییرات

| جدول | تغییر | دلیل |
| --- | --- | --- |
| `SalesDocument.status` | وضعیت `converted` حذف می‌شود؛ پیش‌فاکتور فقط `draft · issued · cancelled` دارد | «تبدیل‌شده» حالا تجمیعی و محاسباتی است (بخش ۲) |
| `SalesDocument` | `closed_at`، `close_reason`، `closed_by` | بستن مانده‌ی پیش‌فاکتور با دلیل |
| `SalesDocument` | `return_type`: `goods` \| `undelivered` (فقط برای مرجوعی) | مرجوعی کالا در برابر کسر از فاکتور بدون کالا |
| `Delivery` | `issue_checks`، `override_reason` | کنترل توقف فروش و سقف اعتبار هنگام صدور حواله |

مهاجرت داده: هر پیش‌فاکتور `converted` → `issued`. مرجوعی‌های موجود → `return_type=goods`. در حال حاضر هیچ سند واقعی‌ای وجود ندارد.

---

## ۲. مقادیر محاسباتی

همه فقط از اسناد **صادرشده** حساب می‌شوند، مگر جایی که «رزرو پیش‌نویس» ذکر شده باشد.

**ردیف پیش‌فاکتور** (`pf`):

```text
invoiced(pf)  = Σ quantity ردیف‌های فاکتور صادرشده با source_line = pf
remaining(pf) = pf.quantity − invoiced(pf)          (اگر پیش‌فاکتور بسته شده: ۰)
```

**وضعیت فاکتورشدن پیش‌فاکتور** (فقط برای `issued`):

| وضعیت | شرط |
| --- | --- |
| بسته‌شده | `closed_at` پر است |
| کامل فاکتورشده | مانده‌ی همه‌ی ردیف‌ها ۰ |
| بخشی فاکتورشده | حداقل یک ردیف فاکتور خورده |
| باز | هیچ ردیف فاکتوری نخورده |

**ردیف فاکتور** (`il`):

```text
D  delivered  = Σ ردیف‌های حواله‌ی صادرشده
R  returned   = Σ ردیف‌های مرجوعی صادرشده با return_type = goods
X  reduced    = Σ ردیف‌های مرجوعی صادرشده با return_type = undelivered
deliverable   = q − D − X
returnable    = D − R
reducible     = q − D − X
```

وضعیت تحویل فاکتور: تحویل کامل وقتی `D + X ≥ q` برای همه‌ی ردیف‌ها؛ تحویل جزئی وقتی `D > 0`؛ در غیر این صورت تحویل نشده.

**رزرو پیش‌نویس:** در سقف‌ها، پیش‌نویس‌های دیگرِ همان نوع هم کم می‌شوند، ولی پیش‌نویسِ خودِ سند کم نمی‌شود. این کار جلوی رزرو دوباره‌ی یک مقدار توسط دو پیش‌نویس را می‌گیرد. هنگام صدور، سقف دوباره فقط با اسناد صادرشده کنترل می‌شود.

## ۳. انتقال‌ها

| انتقال | شرط | محدودیت | اثر |
| --- | --- | --- | --- |
| **تبدیل** پیش‌فاکتور ← پیش‌نویس فاکتور | پیش‌فاکتور صادرشده، نه بسته، مانده > ۰ | — | ردیف‌هایی که مانده دارند با **مقدار = مانده** کپی می‌شوند. قیمت: اگر پیش‌فاکتور در تاریخ امروز معتبر است، قیمت خودش؛ اگر منقضی است، قیمت روز (`pricing.quote`) + هشدار |
| **صدور فاکتور** | پیش‌نویس | ردیف با مبدأ پیش‌فاکتور: `qty ≤ remaining(pf)` (ایراد `proforma_qty`) | وضعیت پیش‌فاکتور خودبه‌خود بخشی یا کامل می‌شود |
| **بستن** پیش‌فاکتور | صادرشده و نه بسته | دلیل الزامی | مانده‌ی همه‌ی ردیف‌ها ۰؛ تبدیل بعدی ممنوع |
| **ابطال** پیش‌فاکتور | صادرشده | فقط اگر هیچ فاکتور صادرشده‌ای ندارد؛ وگرنه «بستن» | — |
| **ابطال** فاکتور | صادرشده | نه حواله‌ی صادرشده، نه تسویه، نه مرجوعی صادرشده (قاعده‌ی فعلی) | مانده‌ی پیش‌فاکتور خودبه‌خود برمی‌گردد |
| **صدور حواله** | فاکتور صادرشده | هر ردیف: `qty ≤ deliverable`؛ کنترل‌های بخش ۴ | — |
| **ابطال حواله** | حواله‌ی صادرشده | پس از ابطال، برای هر ردیف `D_new ≥ R` (ایراد: «روی این کالاها مرجوعی خورده») | مقدار قابل حواله برمی‌گردد |
| **مرجوعی کالا** | فاکتور صادرشده | هر ردیف: `qty ≤ returnable` | کسر از مانده‌ی مشتری و پورسانت؛ در آینده ورود به انبار |
| **کسر تحویل‌نشده** | فاکتور صادرشده، `reducible > 0` | هر ردیف: `qty ≤ reducible`؛ دلیل الزامی | کسر از مانده‌ی مشتری و پورسانت؛ **بدون اثر انبار**؛ فاکتور «تحویل کامل» می‌شود |

## ۴. کنترل‌ها (سطح: ایراد / نیاز به دلیل / هشدار)

| کد | کجا | سطح | شرط |
| --- | --- | --- | --- |
| `proforma_qty` | صدور فاکتور | ایراد | مقدار ردیف بیش از مانده‌ی پیش‌فاکتور |
| `proforma_closed` | صدور فاکتور | ایراد | پیش‌فاکتور مبدأ بسته یا ابطال شده |
| `proforma_price` | صدور فاکتور | نیاز به دلیل | پیش‌فاکتور در `doc_date` فاکتور معتبر است و فی خالص ردیف با فی خالص ردیف پیش‌فاکتور فرق دارد |
| `proforma_expired` | صدور فاکتور | هشدار | پیش‌فاکتور مبدأ منقضی است (قاعده‌ی موجود) |
| `on_hold` | صدور حواله | نیاز به دلیل | فروش به مشتری متوقف است |
| `credit` | صدور حواله | نیاز به دلیل یا هشدار (طبق سیاست) | ریسک کل مشتری بیش از سقف (بدون افزودن فاکتور، که قبلاً حساب شده) |
| `return_qty` | صدور مرجوعی کالا | ایراد | بیش از `returnable` |
| `reduce_qty` | صدور کسر تحویل‌نشده | ایراد | بیش از `reducible` |
| `delivery_returned` | ابطال حواله | ایراد | `D_new < R` |

## ۵. اثر مالی و پورسانت

- هر دو نوع مرجوعی، مانده‌ی مشتری را مثل الان کم می‌کنند: `مانده = فاکتور − مرجوعی‌ها − دریافت`.
- در پورسانت، هر دو نوع با درصد ردیف فاکتور مبدأ و مبلغ منفی حساب می‌شوند (رفتار فعلی).
- سهم پرداخت‌شده‌ی فاکتور: `پرداخت ÷ (مبلغ فاکتور − همه‌ی مرجوعی‌ها)` (رفتار فعلی).
- پیش‌فاکتور هیچ اثر مالی ندارد.

## ۶. API

| مسیر | تغییر |
| --- | --- |
| `POST documents/{id}/convert/` | تبدیل با مانده (بخش ۳)؛ تا مانده > ۰ تکرارپذیر |
| `POST documents/{id}/close/` `{reason}` | جدید: بستن مانده‌ی پیش‌فاکتور |
| `POST documents/{id}/make-return/` `{type: goods \| undelivered}` | پیش‌فرض `goods`؛ مقدار پیش‌فرض = `returnable` یا `reducible` |
| `POST deliveries/{id}/issue/` `{override_reason}` | مثل صدور سند: `400` با `checks` و `needs_reason` |
| `GET documents/{id}/` | برای هر ردیف: پیش‌فاکتور ← `invoiced`، `remaining`؛ فاکتور ← `delivered`، `returned`، `reduced`، `deliverable`، `returnable`. برای سند: `invoicing_state` پیش‌فاکتور |

## ۷. AuditLog

هر انتقال بخش ۳ یک رکورد دارد: `before/after` وضعیت، شماره‌ی سند مبدأ و مقصد، و دلیل هر جا که الزامی است. نمایش خط زمانی سند از همین رکوردها ساخته می‌شود (کار جدا).

## ۸. سناریوهای تست

1. پیش‌فاکتور ۱۰۰۰ ← فاکتور ۷۰۰ صادر ← مانده ۳۰۰، وضعیت «بخشی» ← تبدیل دوم پیش‌نویس ۳۰۰ می‌سازد ← صدور ← «کامل» ← تبدیل سوم رد می‌شود.
2. فاکتور ۸۰۰ از مانده‌ی ۳۰۰ رد می‌شود (`proforma_qty`).
3. ابطال فاکتور ۷۰۰ ← مانده دوباره ۱۰۰۰.
4. بستن پیش‌فاکتور با مانده‌ی ۳۰۰ ← «بسته‌شده»، تبدیل رد، بستن بدون دلیل رد.
5. ابطال پیش‌فاکتوری که فاکتور صادرشده دارد رد می‌شود.
6. پیش‌فاکتور معتبر، قیمت فاکتور متفاوت ← `proforma_price` نیاز به دلیل؛ قیمت برابر ← بدون کنترل.
7. پیش‌فاکتور منقضی ← تبدیل با قیمت روز + هشدار.
8. دو پیش‌نویس فاکتور از یک مانده‌ی ۳۰۰، هر کدام ۲۰۰ ← دومی هنگام صدور رد می‌شود.
9. فاکتور ۱۰۰۰، حواله ۸۰۰ ← مرجوعی کالا ۸۰۰ مجاز، ۸۰۱ رد.
10. همان فاکتور ← کسر تحویل‌نشده ۲۰۰ ← «تحویل کامل»؛ حواله‌ی بعدی رد.
11. حواله ۴۰۰ + ۳۰۰، ابطال ۴۰۰ ← قابل حواله ۷۰۰.
12. حواله ۴۰۰ + ۳۰۰، مرجوعی کالا ۵۰۰ ← ابطال حواله ۴۰۰ رد می‌شود (`delivery_returned`).
13. مشتری در توقف فروش ← صدور حواله بدون دلیل رد، با دلیل صادر و دلیل ثبت می‌شود.
14. مانده‌ی مشتری و پورسانت پس از مرجوعی کالا و کسر تحویل‌نشده، هر دو کم می‌شوند.
15. تست‌های موجود (۲۲ تست) بدون تغییرِ رفتار سبز می‌مانند؛ فقط تست تبدیل یک‌باره با سناریوی ۱ جایگزین می‌شود.

---

## ۹. خارج از این مرحله

- ورود و خروج موجودی انبار: فقط جای اثرش در `goods` و `undelivered` مشخص شده است.
- نمایش خط زمانی سند.
- بستن جداگانه‌ی یک ردیف پیش‌فاکتور؛ فعلاً بستن کل مانده‌ی سند.
